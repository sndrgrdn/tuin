# Prototype

You own the decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.

Speed beats polish here. Code quality does not matter. The rigour goes into picking the right design cheaply.

1. **Name the decision** the prototype exists to make: which layout, interaction or density, or which behaviour, timing or approach. No decision means no prototype; route to Feature.
2. **Gather references** when the design space is open, and let the user pick directions. Skip when the direction is set.
3. **Build it in a scratch directory**, apart from production code, with the lightest stack that shows the idea. For a behaviour or timing question, write the smallest script that exercises it.
4. **Put the variants behind one switcher** (buttons or a key), each labelled (Exhaust the Design Space). Propose a variant the user did not ask for.
5. **Observe each variant** on its surface: screenshots and interaction for a visual decision, logged output or timing for a behavioural one.
6. **Present** the variants, the evidence, the tradeoffs and your recommendation. Hand the chosen direction to Feature.

**Reply:** the variants, the evidence, the tradeoffs, your recommendation and the scratch path. Say plainly that the prototype is throwaway.
